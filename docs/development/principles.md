# 开发原则

1. **业务边界先行。** Git、Issue、PR、工作流和制品复用底座；自有服务负责跨组件交付关系。对外契约和失败行为明确后再写代码。
2. **模块化单体起步。** 模块按身份、项目、Issue、构建、发布、部署、事件划分；不为未来多底座、多租户预建插件系统。
3. **只依赖公开协议。** Gitea 独立运行，禁止直读写其库、嵌入内部 Go 包或调用私有前端接口。确有缺口先留下证据与方案。
4. **权威数据单一。** 上游事实只缓存与关联，自有事实正式持久化；缓存失效与删除来源可追溯。
5. **兼容必须可验证。** 记录精确版本、样例和差异；不以 YAML 解析通过、HTTP 200 或隐藏按钮代替正确语义。
6. **权限在服务端执行。** 登录和资源授权分离；每次写入和后台执行都有有效授权，平台管理员不是所有仓库的隐式用户。
7. **失败是正式状态。** 区分拒绝、失败、取消、过期和结果未知；重试有上限、幂等依据和退避，不吞错或伪造成功。
8. **升级与恢复可设计。** 固定源码 / Digest、保留迁移历史，先添加再迁移再收紧约束；发布迁移不能原地改 checksum。
9. **实现直接。** 使用明确类型和职责；少用万能 manager、重复 DTO 层与空 wrapper。手写源码建议 1000 行以内、上限 1500 行，按真实职责拆分。
10. **工具链统一。** M0 冻结 Go / Node / 包管理器 / 数据库和 Runner 版本；单一来源维护 OpenAPI、schema、锁文件与生成代码。
11. **交互完整。** 加载、空态、失败、失权、重试和长内容与成功路径一起完成；PC / 窄屏 / 键盘都可用。
12. **验证匹配风险。** 小改做相关检查，阶段验收跑真实主路径，发行做安装和恢复。没有业务代码时不创建空成功 CI。

依赖引入须说明用途、维护状态、许可和替换边界；不从兄弟项目搬来秘密、运行配置或整套依赖。自有文本采用 UTF-8 无 BOM、LF 和末尾换行。测试使用合成数据，日志保留诊断所需信息并避免秘密。

当前不选定具体路由库、ORM、组件库或部署 SDK；这些不是必须提前做出的产品决定。工程初始化应先冻结实际需要的最小工具链，不把建议列表一次性全部安装。
