# M0 底座可行性子专题计划

状态：近期执行范围已细化；M0-S01 已取得官方来源证据并形成[本机 Docker 优先方案](m0-s01-baseline.md)，M0-S02 / S03 已开始身份、权限与 Issue 的部分真实验证，见[本机记录](../records/2026-11-01-m0-local-validation.md)。任务状态见[tasks](tasks.md)，当前授权见[current](../status/current.md)。候选不是已支持组合，本计划本身不构成环境或远端动作授权。

目标：在 Go / React 工程初始化前，取得独立 Gitea 与 Runner 公开接口、身份授权和最小交付能力的证据，明确首批 GitHub 兼容范围。阶段预算沿用[路线图](roadmap.md)的 6—10 人日，不把整个 M0 作为一天的承诺。

## 层级、状态与完成口径

本页合并承载四个子专题，各章节的牵头 / 协同归属见[专题索引](topics.md)。M0 是阶段，S01—S04 是子专题，内部准备与验证批次是实施切片；沿用既有任务和验收 ID，不增加递归专题层级。

任务状态唯一维护于 [tasks](tasks.md)，本页规定范围和验收方法；[验收矩阵](acceptance.md)规定上位标准，records 保存实际结果。每次取证注明对应子专题、任务、验收子集和未覆盖面。某批通过不能关闭其余批次或上位产品验收；四项必需范围和 M0 阶段出口都满足后才判断 M0 完成。

## 执行顺序与首批范围

1. M0-S01 先做官方来源静态核查和候选组合选择，准备隔离方案；确认具体资源影响与授权后再建立环境。
2. 使用候选组合推进 M0-S02，优先取得一个普通用户可读写自己的私有资源、另一用户被拒绝及撤权后失效的证据。
3. M0-S03 完成 Issue / Actions / OCI / Release 最小操作；M0-S04 可提前准备样例清单，但差异决策须依赖真实结果。
4. 四项证据合并后冻结支持组合和首批范围。候选变更时复核受影响契约，关键边界失败先决策，再考虑 M1。

M0-02 / M0-03 依赖 M0-01 的候选与隔离准备部分，不要求先完成全阶段最终冻结；M0-03 的受保护资源操作另依赖 M0-02 已确认的用户授权部分。M0-01 在验证期间可保持进行中，最终冻结在阶段收口时完成，避免形成“先验收再启动验证”的循环依赖。

首个执行批次只要求“可复现的候选组合 + 一条真实权限验证链路”；不因此关闭整个 M0-01 / M0-02。若没有可用 IdP、隔离环境或相应授权，交付静态核查与明确的待验证清单，不填写真实通过。

## M0-S01：底座组合与隔离验证准备

- 牵头：TOP-BASE；协同：TOP-OPS、TOP-GOV。
- 对应：M0-01；BASE-01 的版本、来源与环境部分。
- 设计依据：[总体架构](../architecture/overview.md)、[上游与许可](../governance/upstream-and-licensing.md)、[部署策略](../deployment/strategy.md)。
- 当前交付：[候选与本机执行方案](m0-s01-baseline.md)、[初始来源记录](../records/2026-11-01-m0-s01-review.md)和[本机真实证据](../records/2026-11-01-m0-local-validation.md)；环境配置和部分上游取证已落地，最终支持冻结仍待阶段收口。

**场景与输入。** 从当前仅有静态参考、没有运行实例的状态出发，选择一个能验证首版主路径的最小组合。先核对官方发行、版本化文档、OpenAPI、镜像来源、运行条件和许可；已有 Gitea v28.2.0 参考不能直接当作已部署或已验收版本。

**方案与范围。**

| 工作 | 应记录内容 |
| --- | --- |
| 底座与 Runner | 精确发行版 / 源码提交、镜像坐标与 Digest、平台架构、配套运行时；Runner 单独核实版本与来源 |
| 产品工具链 | Go、Node、包管理器、PostgreSQL、Docker / Compose 的候选精确版本及用途；本轮实际不用的工具不提前安装 |
| 接口与来源 | 对应版本 OpenAPI 来源、获取日期与校验摘要，官方文档及许可证入口；候选与已验证分别标记 |
| 隔离环境 | 宿主平台、独立目录 / 网络 / 端口、存储与预估资源、合成账号 / 数据、IdP 选择、启动和停止 / 清理方案 |

不预选 ORM、路由库、组件库或整套 SDK；M1 初始化前，按 M0 结论收敛最小工具链。验证宿主和将来发行目标分别记录，macOS / arm64 上成功不能外推 Linux x86_64 安装通过。

**成功与失败边界。** 候选的版本、来源和平台可复现，实际获取的镜像与 API 描述可核对；不能只固定可移动标签。镜像不可用、平台不符、公开接口缺失或许可待核时保留失败，不自动换版本、关闭验证或转用底座私有接口。身份验证环境先启动所需底座 / IdP，Runner 在需要执行工作流时再启动。

**交付与证据。** 形成候选组合表、隔离执行说明和来源记录；实际启动后记录命令、目录、PID / 容器、端口、数据归属、资源影响与清理结果。M0-01 的最终冻结还依赖 M0-S02—S04 的结果，不把准备方案当成 BASE-01 全项通过。

## M0-S02：身份与私有权限可行性

- 牵头：TOP-IAM；协同：TOP-BASE。
- 对应：M0-02；IAM-01、IAM-02 的上游协议与授权证据。
- 依赖：M0-S01 已固定可复现候选，隔离实例 / IdP / 账号及具体操作已获授权。
- 设计依据：[身份与访问](../architecture/identity-access.md)。
- 本批切片：按[ADR 0003](../adr/0003-gitea-authorization-profiles.md)收敛 Gitea 三种用途组合与联网前白名单，继续 confidential client、刷新 / 撤销 / 过期验证；[实际结果](../records/2026-11-01-m0-auth-profile-validation.md)保留原始 scope 及新生命周期差异，不另建子专题或关闭全项 IAM 验收。

**场景与输入。** 用户通过标准 IdP 认证，再以自己的 Gitea OAuth 授权访问私有资源。使用至少两个普通用户、隔离组织 / 私有仓库及撤权前后状态；管理员仅用于配置，不作为访问能力的唯一证据。Radish 可作为候选 IdP，但不能成为自部署硬依赖。

**最小方案与验收步骤。**

| 范围 | 操作与预期 |
| --- | --- |
| OIDC 能力 | 验证 Discovery、issuer、JWKS、授权码与 PKCE S256，以及 state / nonce / audience / 过期等适用校验；标明实际由谁执行校验，不把普通 OAuth 用户信息等同标准 OIDC |
| Gitea OAuth | 记录申请与实际授予 scope、Token 生命周期及撤销能力；验证 read / write 的真实权限，不假定 `openid email profile` 只提供身份权限 |
| 绑定前提 | 核实 issuer + sub、底座实例 + 用户 ID 的稳定来源，以及双方确认所需公开接口；同邮箱不同身份不能自动合并 |
| 正向访问 | 普通用户读取自己的私有资源并完成一次受权写入，回读确认结果 |
| 越权与撤权 | 第二用户猜测同一资源标识、无权限写入、撤销授权 / 仓库权限后重试；记录拒绝、过期及无法核实的真实行为 |

验证可使用受控协议客户端与最小样例，不提前建立自有会话、Token 库或完整登录服务。上游暂不支持的负向注入标记未覆盖；浏览器 Cookie、CSRF、会话轮换、绑定交互、加密存储和后台作业撤权仍在 M1 实现后验收。

**失败停止线。** Token 超出预期权限、撤权仍可访问、只能靠管理员凭据写入、没有标准 OIDC 或公开绑定接口不足时，保存脱敏证据并记录差异。不得按邮箱自动绑定、用服务账号绕过或把 UI 隐藏当作拒绝；关键问题未解决不进入依赖它的工程实现。

**交付与证据。** 记录角色 / 资源矩阵、scope、版本、脱敏请求结果、撤权时点及未覆盖项。只确认上游可行部分，不关闭整个 IAM-01 / IAM-02 产品验收。

**生命周期切片（2026-11-04 接续）。** 三种受控组合沿用 M0-02，不新建子专题或产品服务；两项历史差异的定位与处理见[本批记录](../records/2026-11-04-m0-lifecycle-validation.md)及[ADR 0003 补充](../adr/0003-gitea-authorization-profiles.md#2026-11-04-生命周期补充决定)，实际完成范围以 records 和 tasks 为准：

1. 对照原配置与显式关闭表单 / 查询串资源鉴权的配置，核查 introspection 的目标 `token` 是否先被中间件处理；保留原始状态、正文类型和最终路径。区分客户端认证错误、Token 失效、账号被拒绝和网络无法核实；不以 HTTP 200、active metadata、空 scope 或无上限重试兜底。禁用账号仍可刷新保留为上游差异，以在线账号复核拒绝使用。
2. 验证 refresh token 自身到期和并发轮换 / 重放；真实时间等待单独预算，不修改系统时钟。记录哪些请求成功、后继凭据是否仍受只读 / 对象权限约束；写入超时或结果未知先停止依赖操作，不盲重放旧 Token。未跑完的长时用例保持待验证。
3. 通过原生用户设置页验证单用户撤销，确保共享应用、同应用另一用户、同用户其他应用和独立身份授权不受影响；撤销发生在 access token 正常到期前。固定 OpenAPI 无单用户 grant 撤销接口的缺口须明确记录，不包装私有前端接口或删除整个共享应用。账号禁用 / 恢复、显式重新同意及旧凭据仍失效分别记录；产品解绑、会话、加密存储和后台作业取消仍在 M1 实现后验收。

每批使用新归属和合成数据，记录配置回读 / 哈希、实际加载源码、预期 / 实际、未覆盖与 cleanup；原始 `discovery`、旧配置 `lifecycle-baseline` 和受控结果分开。提取共享探针后须在最终源码上回归已有组合；文件存在或本地通过不能替代真实结果。先收口身份关键边界，再补 M0-S03 的其他 Issue 操作；Runner 保持暂停，不因上述事项安排自动启动。

## M0-S03：Issue 与交付接口最小验证

- 牵头：TOP-BASE；协同：TOP-WORKBENCH、TOP-COMPAT、TOP-DELIVERY。
- 对应：M0-03；BASE-01。
- 依赖：M0-S01 的候选环境；受保护资源操作沿用 M0-S02 确认的用户授权，不以管理员捷径替代。
- 设计依据：[工作台与 Issue](../architecture/workbench-and-issues.md)、[GitHub 兼容](../architecture/github-compatibility.md)、[交付链路](../architecture/delivery-flow.md)。

**场景与最小样例。** 用隔离仓库证明公开接口足以支持首版用例，不建设工作台或部署生产环境。

| 能力 | 成功路径 | 必查失败 / 权限边界 |
| --- | --- | --- |
| Issue | 创建、列表 / 分页、详情、编辑、评论、关闭 / 重开；标签 / 负责人 / 里程碑的查询与合法分配 | 列表排除 PR；普通用户越权、非法关联对象、资源删除；超时结果先回查 |
| Actions | push / Tag / 手动触发，查询 run / job / attempt、取消 / 重跑及日志获取 | 无 Runner、执行失败 / 取消 / 失联分别记录；触发回执与实际 run 可关联，不取“最新 run”代替 |
| OCI | 构建 / 推送一个最小样例镜像，Registry 回读 Digest，以固定 Digest 拉取并关联源码 / run | 私有组织包由第二用户直接 pull 验证拒绝；包权限不从关联仓库权限推导 |
| Release | 草稿、说明、附件上传 / 下载校验、发布及回读，关联固定 Tag / SHA | 无权访问、重复请求、部分上传 / 超时后的查询能力；不盲重试写操作 |

本轮一个最小镜像样例只验证协议，不代替 M4 五组件清单、幂等恢复和 M5 测试至生产晋级。受控故障注入仅在本任务隔离数据上执行，操作结果未知先对账。

**Issue 切片（2026-11-04）。** 已新增[Issue / 失败边界证据](../records/2026-11-04-m0-issue-validation.md)与[ADR 0004](../adr/0004-issue-validation-and-reconciliation.md)：覆盖本表的个人仓库 Issue 主路径、普通用户权限、真实 PR 排除及响应丢失，原始非法输入 / 筛选 / 部分写入差异继续保留。前检与对账属于受控验证，不表示上游已修复、完整 ISSUE-01 已通过或已建立产品幂等。Actions / OCI / Release 仍按原范围待取证；不得以本批部分证据关闭整个 BASE-01 / M0-03。

**交付与证据。** 按能力记录版本、端点、权限、合成数据、请求 / 回读、失败与未知结果，以及需要工作台补足的部分。若关键接口缺失或无法安全实现，先提出范围 / 方案差异，不直接扩为底座补丁或重写执行器。

## M0-S04：首批兼容范围与缺口决策

- 牵头：TOP-COMPAT；协同：TOP-IAM、TOP-DELIVERY。
- 对应：M0-04；COMP-01 的样例冻结与差异基线，完整兼容验收在 M3。
- 依赖：M0-S02、M0-S03 的真实结果；样例清单可提前静态整理。
- 设计依据：[GitHub 兼容策略及原有矩阵](../architecture/github-compatibility.md)。

**输入与方案。** 从原有矩阵选择首批最小样例，不复制一套兼容状态。优先覆盖 checkout、Go / Node 工具链、一次镜像构建推送、Release / 附件，以及项目实际需要的仓库只读、Issue、Actions、Release REST 调用。缓存、附件 Action 等候选须逐项决定是否列入首批，未选中项明确延期，不承诺市场全部 Action。

固定 GitHub REST 对照版本、客户端版本、Action 仓库 / commit、运行平台、原始工作流及预期输出。版本支持状态执行时核对官方来源，不沿用静态参考作为当前结论。权限负例至少包含 permissions、environment、concurrency、fork PR 秘密访问；不能只测 YAML 是否接受。

**成功与失败边界。** 每项使用既有状态：待验证、直接兼容、需配置、需适配、不支持。只有取得对应行为证据才能离开待验证；只固定样例而未运行时仍为待验证。静默忽略关键安全字段判失败，受控模板的补偿不等于任意工作流兼容。

**交付与证据。** 在既有兼容专题维护首批范围，records 保存原样例、diff、预期 / 实际与限制；影响公开协议、权限、零核心补丁目标或明显成本的缺口形成 ADR / 所有者决定。证据不足不宣传兼容，不为了进入 M1 静默缩减权限要求。

## 阶段出口与交接

- M0-01—M0-04 按各自范围有可定位证据，候选组合已依据结果冻结，未通过项有明确处理。
- BASE-01 的真实上游最小能力成立；身份与兼容的上游部分有结论，后续产品验收范围仍保留。
- 关键权限、公开接口与零核心补丁目标的冲突先决策；不能通过延后关键缺口宣称晋级。
- 更新 tasks、current、相关设计与 records，说明 M1 可开始的具体范围、仍需实现 / 验证的部分和资源交接。
- 结束默认停止并清理本任务资源；需保留环境时明确目录、端口、数据、秘密保管方式和停止责任。

证据字段沿用[验证专题](../development/validation.md)，不新建第二套结果格式。治理收尾仍按[专题索引](topics.md)和原 G0 任务推进，不由本计划隐式授权测试 PR、Ruleset 写入、提交、推送、发布或部署。
