# 协作与授权

本页补充根协作入口的执行细节。用户明确要求优先；既有授权在目标、范围和影响未变时持续有效。任务类型、范围与当前事实以用户要求和 current 为起点，不由兄弟项目的不同协作习惯覆盖。

## 启动与工作区判断

1. 判断请求是说明、审查、诊断、规划、实现、验证还是发布。解释和审查默认只读；明确要求修改后，完成范围内工作，不停留在计划。
2. 阅读 README、current 和相关专题，核对现有目录、入口、测试与脚本。查找已有职责与命名，避免重复配置和第二套实现。
3. 有 Git 时检查 `git status --short --branch`、工作树与暂存 diff、未跟踪文件、分支和必要的跟踪关系；没有 Git、没有提交、没有 upstream、没有远端是不同状态。
4. 分清用户、并行任务和本次改动；与当前任务无关的内容原样保留。出现直接冲突时先读明白差异，不能自动 stash、reset 或覆盖来得到理想工作区。
5. 本地远端引用可能过期；未 fetch 时不能把 ahead / behind 当作服务端实时事实。没有远端时只验证本地拓扑，不伪造远端同步结论。
6. 给本批确定可检查的目标和边界；已有专题足够时直接沿用，缺少关键输入才澄清。

## 什么时候澄清

| 情况 | 处理 |
| --- | --- |
| 目标明确，只有常规实现细节未定 | 自行判断并完成必要验证 |
| 已授权方案仍覆盖动作、目标和副作用 | 继续执行，不因换轮次重复确认 |
| 不同解释会改变产品、公开接口、数据、权限、许可或外部影响 | 说明具体差异和选择影响，确认后推进相关部分 |
| 存在可独立完成的已授权工作 | 先继续这部分，不把整个任务停在等待上 |
| 新动作是相邻但未覆盖的外部写入 | 明确目标与副作用，不能从提交推导 push 或从 push 推导发布 |
| 工具失败、结果未知或环境阻塞 | 保留错误并核实状态，不以反复尝试替代判断 |

授权以具体动作的覆盖范围判断，不把每个 shell 命令都变成新的审批点；反过来，也不把“继续推进”解释成无限扩展到外部系统。

## 实施粒度

用户可见功能、重要页面与跨模块能力先明确使用场景、输入、权限、状态变化、成功、失败、兼容与验收。小修沿用最近专题，不创建只有标题的任务卡或为一次性沟通增加正式文档。

先理解现有调用与数据归属，再修改根因。可交付切片要覆盖实际使用与关键失败边界；范围控制不等于只修表面，也不等于顺带重构、换依赖或搬目录。范围外但值得处理的问题记录原因，不混入本批。

仅在用户或适用指令明确要求时使用子代理；并行时明确文件归属、接口、验收和整合责任。共享工作区不能假定其他任务尚未写入；整合前重新检查实际差异。

## 执行边界

| 动作 | 执行条件 |
| --- | --- |
| 范围内文件读写、只读 Git、检查 / 构建 / 测试 | 按任务授权执行 |
| 安装、升级、移除依赖，修改 lockfile，下载大文件 | 说明用途、版本、落盘与资源影响，已有授权须覆盖 |
| 长驻服务、开发服务器、桌面 / 交互式程序、高资源任务 | 说明命令、目录、端口、时长、资源与停止方式，已有授权须覆盖 |
| Git 初始化、精确暂存、提交、分支操作 | 依据具体任务和仓库治理核对授权；不自动重写历史 |
| 远端创建、push、PR / 合并、Rulesets / 设置 / Secrets | 对应外部目标和写入需有覆盖授权 |
| tag、包 / 镜像发布、Release、部署、外发消息 | 分别核对授权，前一步成功不代表下一步获准 |
| 跨项目写入、数据删除、系统 / 全局配置变更 | 不由普通项目任务推导，必须有明确覆盖 |

本地检查可能间接安装依赖、拉镜像或启动服务，先读入口确认实际副作用，不能只因命令名叫 test 就视为纯检查。用户授权启动某服务时，复用其已确认的版本、目录与影响；变化后再判断是否扩大授权范围。

不修改全局 Git 身份、系统权限、证书、密钥链、运行时或编辑器设置掩盖项目问题。受沙盒、网络、证书或 PATH 限制时记录原始原因，按同一已授权目标申请最小权限；不自动降级签名、TLS 或安全检查。

## 资源与敏感数据

- 自建服务记录 PID、端口、目录、启动命令和停止方式。结束默认停止本任务资源，用户要求保留时交接用途和清理方式。
- 已占用端口先识别归属；不杀掉其他任务进程，不使用归属未知的运行实例冒充本任务环境。
- 临时验证使用独立目录、隔离账号与合成数据，不覆盖用户工作文件、正式数据库或生产配置。
- 清理前解析实际路径，核对在本任务范围内；不对仓库根、用户目录、空变量或宽泛通配符执行递归删除、覆盖或移动。
- 秘密通过受控配置机制提供，避免进入 shell 历史、命令参数、日志、截图、fixture、报告或提交；错误输出也需要脱敏。
- `.gitignore` 只控制默认跟踪，不撤销已经泄漏的秘密。发现真实泄漏时停止传播、私下报告并处理凭据，不把删文件当作恢复完成。

## 验证与证据

按风险选择检查，不机械地每步跑全量。治理变更验证文本与政策一致性；实现变更验证行为和失败边界；跨模块变更补主路径；发行与部署增加实际安装、迁移、恢复和权限验收。具体入口见[验证专题](../development/validation.md)和[current](../status/current.md)。

已有检查通过后，仅因新改动、失败或未解决风险补测。不能通过删断言、跳过 job、关闭签名验证、放宽预期或把真实依赖换成假成功来通过门禁；需调整规范时明确原因并同步相关验收。

记录命令、版本、环境、数据范围、预期与实际、失败原因和未验证部分。本地文件存在、构建通过、Mock 测试、真实底座契约、远端配置与生产行为分别表述。没有服务或凭据时准确写明未执行，不从离线结果外推可用性。

UI 根据任务覆盖 PC / 窄屏、键盘与焦点、长内容、加载 / 空态 / 错误；截图和静态结果不能替代真实交互。联调前确认服务归属，权限测试不只依赖管理员账号。

外部请求超时不等于未执行；Issue、Release、部署等写入先查询实际状态，再按幂等依据和上限决定后续动作，不盲重试。

## 完成与交接

交付前重新检查 diff、暂存区、未跟踪与被忽略的本任务产物，确认没有无关文件、秘密、缓存、意外换行或权限变化。提交时精确选择路径，不能为了清空工作区带上用户改动。

同步已有专题、任务、current 和必要记录。结论说明实际完成、验证与限制、剩余工作、下一步、后台资源以及 Git 提交 / 分支 / 推送状态。历史长输出和证据进入 records，不复制回 AGENTS / CLAUDE，不把内部对话或私密会话信息写入项目。

交接的待办要能直接执行：写清缺少什么证据、依赖什么条件以及完成标准；已经覆盖的授权不要换一种措辞重新索要。根入口增补与内容归位见[文档治理](documentation.md)。
