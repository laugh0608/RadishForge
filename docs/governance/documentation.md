# 文档治理

## 单一来源

| 内容 | 正式位置 |
| --- | --- |
| 产品定位、功能范围 | product-plan.md |
| 数据、接口、交付和身份设计 | architecture/ |
| 开发、测试和运维原则 | development/、deployment/ |
| 长期协作、上游、许可与版本 | governance/ |
| 有原因和替代方案的重要决定 | adr/ |
| 目标顺序、任务、验收编号 | planning/ |
| 专题 / 子专题路由与阶段对应 | planning/topics.md；近期子专题在 planning/ 按需展开 |
| 当前实现、下一步、临时停止线 | status/current.md |
| 已执行动作和实际证据 | records/ |
| 外部资料及兄弟项目来源 | references/ |

README 和根协作文件只提供稳定简介、约束与路由，不堆积进度、日志或临时版本号。任务状态由 planning/tasks 维护，current 仅引用当前重点，不复制完整清单。

## 整体规划、大专题与子专题

三级规划与执行证据分别维护：

| 层级 | 唯一职责 | 本仓入口 |
| --- | --- | --- |
| 整体规划 | 产品目标、范围、能力地图、优先级、里程碑与阶段出口 | [产品规划](../product-plan.md)、[路线图](../planning/roadmap.md) |
| 大专题 | 能力边界、权威设计、跨专题依赖、子专题清单及目标版本完成条件 | [专题索引](../planning/topics.md)中的 TOP-*，正文复用 architecture、deployment、governance |
| 子专题 | 一个明确功能或可交付工作包的场景、方案、范围、失败边界和分期验收 | 近期计划中的 M0-S01—M0-S04 等既有文档或稳定章节 |
| 执行与证据 | 任务状态、当前重点、实际验证与限制 | [tasks](../planning/tasks.md)、[current](../status/current.md)、records |

M0—M6 是时间与依赖维度，专题是能力维度；一个专题可以跨阶段。执行与证据贯穿三级，不构成第四级规划。子专题可一次交付，也可在其内部按切片分期；切片、任务和附属设计文档不再递归为新的专题层级。

每个子专题只指定一个牵头大专题，跨能力关系列为协同；每项任务只维护一份状态。专题索引连接归属、阶段、设计、任务状态和验收入口，不复制设计正文或完整任务表。现有 TOP-*、M0-S*、任务与验收 ID 保留，废弃编号保留去向、不重新利用。

## 专题最小内容

大专题至少明确用户价值、范围与非目标、权威设计与数据 / 接口边界、依赖、子专题清单和目标版本完成条件。当前 TOP-* 通过索引及其链接的既有设计共同承载这些内容，不要求每个大专题再建一份文件。

子专题进入实施前按以下清单补齐；同一计划内可用稳定章节承载多个子专题，小目标可合并条目：

| 内容 | 应写清的问题 |
| --- | --- |
| 归属与目标 | 牵头 / 协同专题、阶段、用户场景、目标交付范围 |
| 输入与依赖 | 已有实现、数据与权限来源、依赖哪些已取得证据或待决条件 |
| 设计与边界 | 方案依据、输入输出、正常 / 失败 / 恢复路径、非目标及兼容约束 |
| 切片与任务 | 每期交付、保留的任务 ID、依赖、完成条件与唯一状态来源 |
| 验收与证据 | 标准所在位置、对应验收 ID、验证方法、环境、实际结果和未验证面 |
| 接续 | 剩余缺口、阻塞原因 / 解除条件、下一步与历史证据入口 |

只细化当前与近期工作；远期先登记能力边界和启动条件，不创建空文档。局部修错沿用所属专题。静态准备、真实执行和发布分别取证，不以文档存在关闭功能任务。

## 进度与验收归属

- 任务状态只在 [tasks](../planning/tasks.md)维护；子专题引用任务 ID 与证据，不另建同一任务状态副本。子专题当前交付状态由其关联任务和该期验收共同判断。
- 通过标准只在[验收矩阵](../planning/acceptance.md)及其引用的正式设计中维护；records 记录实际结果，不能反向以历史通过缩减现行标准。
- current 保留有来源的当前能力、活跃子专题、阻塞、下一步与停止线；摘要注明范围及证据，不复制完整任务清单。
- 子专题某一期完成不代表整个子专题或大专题结束；明确“哪一期、哪种环境、哪些标准”已验收。大专题按目标版本所需子专题和跨专题主路径判断，不按文件数、任务勾选数推算完成率。
- 范围增加时新增切片或明确修订范围，保留旧完成事实；被替代方案标明替代关系，不把历史结论改写成新一轮验收。

新增、调整或完成子专题时，同批核对专题索引、任务 / 验收映射和 current；设计变化更新原专题，长期重要取舍进入 ADR，实际结果进入 records。文档整理不改变产品范围、排期、既有执行授权或未通过的门槛。

## 入口规范

AGENTS.md 与 CLAUDE.md 除第一行标题外逐字一致。建议不超过 180 行，硬上限 250 行；专题细节下沉，不删掉必须在启动时知道的授权边界。

新增根入口规则须同时满足：跨任务成立、跨阶段成立、必须在读取专题前生效、无法仅靠路由可靠承载。细化时补可执行的判断和边界，不单纯增加口号或重复专题全文。

授权、工作区保护和共享历史等立即生效的约束放根入口；动作矩阵、资源清理步骤和交接细节放 collaboration；命令与版本放 current 或对应专题。修改任一根入口须同步另一份，并运行 `python3 scripts/check-repo.py`。

正文默认中文；文件名、目录和稳定标识使用英文。自有文本采用 UTF-8 无 BOM、LF、末尾换行；Markdown 使用相对链接。目录中的示例结构必须标明尚未创建，避免断链。

## 状态词

三类状态分别表达，不能用一列“完成”混合设计、执行和交付：

| 维度 | 状态与含义 |
| --- | --- |
| 方案 | 草案 / 待决定：尚待收敛；已确认：指定范围已接受；已替代：保留替代入口 |
| 执行 | 待开始、进行中、待验收、已完成；受阻、暂停或取消分别记录原因和恢复条件 / 去向 |
| 验证与交付事实 | 静态核查、本地测试、真实上游集成、目标平台验收、已发布等分别说明范围与证据，不互相推导 |

tasks 沿用“阻塞”表示受阻；已有“规划”“本地验证”等表述保留其原范围，不能因统一术语自动升级状态。待验收表示指定实现已交付但必需验收未齐；已完成必须满足该任务或该期的完成标准。已发布须有实际回执，已确认设计不代表已实现。

每项验收记录精确版本、环境、数据范围、操作、结果、失败证据和未验证面。历史记录保留；重大调整通过新 ADR 或明确 supersedes 关系说明，不改写旧事实。
