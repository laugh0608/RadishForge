# 文档治理

## 单一来源

| 内容 | 正式位置 |
| --- | --- |
| 产品定位、功能范围 | product-plan.md |
| 数据、接口、交付和身份设计 | architecture/ |
| 开发、测试和运维原则 | development/、deployment/ |
| 长期协作、上游、许可与版本 | governance/ |
| 有原因和替代方案的重要决定 | adr/ |
| 目标顺序、任务、验收编号 | planning/ |
| 专题 / 子专题路由与阶段对应 | planning/topics.md；近期子专题在 planning/ 按需展开 |
| 当前实现、下一步、临时停止线 | status/current.md |
| 已执行动作和实际证据 | records/ |
| 外部资料及兄弟项目来源 | references/ |

README 和根协作文件只提供稳定简介、约束与路由，不堆积进度、日志或临时版本号。任务状态由 planning/tasks 维护，current 仅引用当前重点，不复制完整清单。

## 整体规划、大专题与子专题

整体规划管理方向、首版范围、优先级和阶段出口；大专题按能力组织边界、设计依据、依赖与子专题清单；子专题管理一批可交付范围和执行验收。M0—M6 是阶段维度，不以阶段号代替能力专题。

[专题索引](../planning/topics.md)统一维护大专题与任务 / 阶段 / 验收的对应及子专题清单，设计正文复用 architecture、deployment、governance 等既有文件。tasks 是任务状态的单一来源；专题文档不复制整套状态表，current 只指向当前活跃或下一项子专题，records 只保存已执行证据。

只细化近期工作，不为远期能力提前创建空文档。子专题执行前须明确场景、输入、依赖、方案、范围、成功 / 失败边界、任务 / 验收与证据要求；静态准备和真实执行分开记录。相关范围足够紧密时可在同一计划中分节，不要求每项单独建文件。

新增、调整或完成子专题时，同批核对专题索引、任务 / 验收映射和 current；设计变化更新原专题，长期重要取舍进入 ADR，真实结果进入 records。已有稳定任务与验收 ID 保留，不为了层级整理重新编号或以文档存在关闭功能任务。

## 入口规范

AGENTS.md 与 CLAUDE.md 除第一行标题外逐字一致。建议不超过 180 行，硬上限 250 行；专题细节下沉，不删掉必须在启动时知道的授权边界。

新增根入口规则须同时满足：跨任务成立、跨阶段成立、必须在读取专题前生效、无法仅靠路由可靠承载。细化时补可执行的判断和边界，不单纯增加口号或重复专题全文。

授权、工作区保护和共享历史等立即生效的约束放根入口；动作矩阵、资源清理步骤和交接细节放 collaboration；命令与版本放 current 或对应专题。修改任一根入口须同步另一份，并运行 `python3 scripts/check-repo.py`。

正文默认中文；文件名、目录和稳定标识使用英文。自有文本采用 UTF-8 无 BOM、LF、末尾换行；Markdown 使用相对链接。目录中的示例结构必须标明尚未创建，避免断链。

## 状态词

- 已确认：用户已确定的产品或工程方向。
- 规划：尚未实现的方案与任务。
- 静态核查：看过官方文档 / 源码，未运行。
- 本地验证：已运行指定范围，不外推到生产。
- 已发布：必须有实际外部回执或记录。
- 待决定：需要后续证据或所有者决定，不假装已经冻结。

每项验收记录精确版本、环境、数据范围、操作、结果、失败证据和未验证面。历史记录保留；重大调整通过新 ADR 或明确 supersedes 关系说明，不改写旧事实。
