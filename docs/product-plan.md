# 产品规划

日期：2026-10-29。本文为已确认方向下的首版规划，所有功能均未实现。

## 定位

RadishForge（萝卜锻坊）是从代码到可交付版本的自托管研发工作台。以 Gitea 管理 Git 与研发事实，以独立 Go 服务组织发布与部署，以 TypeScript / React 提供统一入口。适用于个人开发者和小型工程团队，也考虑客户私有化安装。

首个完整场景：开发者推送一个 Tag，构建五个服务镜像，将精确 Digest 和提交关联为一个 Release，在工作台明确发起测试部署，验证后将同一组制品晋级生产。镜像数量是验收样例，不是产品硬编码限制。

## 首版范围

| 领域 | 首版目标 | 保留的原生入口 / 后续范围 |
| --- | --- | --- |
| 登录与身份 | 标准 OIDC；Gitea OAuth 授权；显式绑定账号与撤销 | SCIM、复杂企业目录同步后续评估 |
| 项目与代码 | 关联一个或多个仓库，文件阅读、分支、Tag、提交、PR 摘要 | 复杂 Diff、行内评审、冲突处理、保护规则使用 Gitea |
| Issue | 列表、筛选、详情、创建、编辑、评论、开关状态、标签、负责人、里程碑 | 跨仓库看板、复杂工作项层级后续评估 |
| CI / Actions | 事件构建、手动触发、状态、任务、取消、重跑、日志下载 | 原生实时日志与复杂排查入口；精确兼容范围另验收 |
| 镜像与制品 | OCI 推拉、版本与 Digest、来源提交及构建关联 | 独立企业 Registry、高级保留策略后续评估 |
| Release | 草稿、说明、附件、多组件清单、发布前检查、失败恢复 | 不以 Tag 存在或单个镜像完成判定全部发布成功 |
| CD | 测试 / 生产环境、手动生产部署、Compose、健康检查、历史与回退记录 | 多级审批、Kubernetes、渐进发布、高可用后续评估 |
| 安装与运维 | 固定镜像、运行时配置、备份、迁移、恢复、底座升级演练 | 不要求在线依赖兄弟产品 |
| GitHub 兼容 | 工作流 / Action、API / Webhook、权限语义分层验证 | 全面 GitHub API、GraphQL、Apps、官方 Runner 协议不列首版承诺 |

## 家族分工

- RadishForge：代码、构建、制品、版本、部署结果。
- RadishNexus：讨论、决策、协作文档及团队协作。双方通过链接和事件关联，不复制一套 Issue 权威数据。
- Radish：可以作为 OIDC 身份提供方；RadishForge 同时支持其他符合约定的发行方。
- RadishInk：参考其上游来源治理和运行时配置模式，不继承编辑器功能与部署限制。
- RadishX：提供家族名称与品牌参考；`forge.radishx.com` 仅为候选地址，本轮不修改其项目矩阵或 DNS。

## 成功标准

新用户能通过 OIDC 登录、绑定 Gitea 账号、处理 Issue，并将一次提交追踪至构建、镜像、Release 和环境部署。失权、失败、取消、部分完成与状态未知均有清楚表现；从备份恢复后仍能解释“当前环境运行哪个版本”。具体通过条件见[验收矩阵](planning/acceptance.md)。

## 非目标与待决定项

首版不重写 Git 存储、流水线执行器和完整代码评审 UI，不直接耦合 Gitea 数据库，不做公有云多租户计费或超大规模调度。

待 M0 冻结：Gitea / Runner / 工具链精确版本、GitHub API 对照版本和首批端点、Action 版本与提交、部署宿主矩阵、OIDC 发行方联测组合。最终自有代码许可、首个客户交付渠道及真实域名由所有者决定；这些不阻止当前文档交付。
